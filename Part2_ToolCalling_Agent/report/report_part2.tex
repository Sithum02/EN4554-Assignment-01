\section{Setup}
\textbf{Agent:} Qwen2.5-0.5B-Instruct (494M) with its own chat template (tool schemas in the system turn; each call is a JSON name and arguments inside \tc{<tool\_call>} tags). The loop generates greedily, runs the calls, feeds the results back and stops at a plain-text answer (at most 4 turns). \textbf{Tools} (made-up data, ``today'' = Tue 10 Mar 2026): \tc{get\_weather(city, unit=celsius)} for 18 cities, \tc{get\_events(date)} for a March calendar, \tc{convert\_units(value, from\_unit, to\_unit)} for 15 units, and \tc{find\_contact(name)} for 16 fictional people. \textbf{Data} (template-generated): train 688 (110 per tool, 60 two-step contact\,$\to$\,weather, 40 two-city, 148 no-tool); test 100 (15 per tool, 8 two-step, 5 two-city, 27 no-tool). The test phrasings and date formats never occur in training (``Mar 18'' vs.\ ``18 March'', checked). \textbf{LoRA:} $r{=}16$, $\alpha{=}32$, dropout 0.05 on all attention and MLP projections (8.8M trainable, 1.75\%), AdamW, lr $2{\times}10^{-4}$ (5\% warm-up, linear decay), 2 epochs (172 steps), batch 8, fp16, seed 42; the loss covers only the assistant's tokens (its calls and answers). Training took 4.6\,min on a T4. A third condition gives the base model a \textbf{better prompt}: rules on when to call, the date format and chaining, plus one example call. \textbf{Metrics:} \emph{validity}: at least one call, and every call parses with a known tool, its required arguments and correct types; \emph{accuracy}: valid, and exactly the reference calls up to spelling (both over 73 tool requests); \emph{abstention}: no call on the 27 no-tool requests; \emph{task success}: the final answer states the facts the tools return (or the known answer), with no call when none is needed. Code: notebook \texttt{agent\_tool\_calling.ipynb}.

LoRA mainly learns \emph{whether} and \emph{in what order} to call: abstention rises from 30\% to 96\%, and two-step requests go from 0/8 to 6/8 fully correct. Part of the accuracy gain is only a convention. In 18 of the 23 requests where it calls \tc{get\_weather} unasked for a unit, the base model adds \tc{unit="fahrenheit"}, although the tool's default is Celsius. If we accept that, LoRA's gain is $+8.2$ in accuracy and $+14$ [$+3$, $+25$] in task success. Two scoring rules were added after reading the outputs and applied to every model. A free day may be reported as ``I don't/couldn't find any events'' (+5 for the better prompt), and a weekday named in an answer must be the right one ($-8$ for LoRA).

\begin{itemize}
\item \textbf{Fixed.} \emph{Unnecessary calls}: the base model reaches for the nearest tool, e.g.\ \tc{get\_weather(city="Earth")} for ``Which planet is closest to the sun?'', \tc{find\_contact(name="Poland")} for a capital, and the nonexistent tools \tc{add} and \tc{subtract} for arithmetic. \emph{Wrong arguments}: 13 are the unrequested \textdegree F. The other 7 are two-step requests that skip \tc{find\_contact}; six of them pass the person as the city (\tc{get\_weather(city="Emma Dubois")}).
\item \textbf{Not fixed (7).} Two two-step requests skip \tc{find\_contact} and guess London. Two ``Which is warmer, X or Y?'' requests make only the first call (the baseline made both, in \textdegree F). ``What's going on today'' goes to \tc{get\_weather}. ``Add 125 and 250'' calls an invented \tc{add\_numbers}. ``Closest planet to the sun'' is answered ``Jupiter''.
\item \textbf{Introduced (8): invented weekdays.} For example, ``You have nothing scheduled on Saturday, 26 March'', which is a Thursday. LoRA names a weekday in 14 answers and gets 8 wrong; the base model never names one. The cause is our data: 110 of the 688 training answers contain a weekday that the generator computed and that no tool returns, so LoRA learned to write one and has to guess it. Training answers should state only facts present in the context (not re-run).
\end{itemize}

\section{Would a better prompt alone have been enough?}
No: the better prompt fixed a convention (unrequested \textdegree F fell from 18/23 to 3/22) but not the decisions. Abstention stayed at 29.6\%, two-step requests at 0/8, and its example date (2026-03-11) leaked into 5 unrelated calls, so its task success did not differ from the baseline's ($+4$ [$-4$, $+12$]). LoRA changed exactly those decisions, though it also copies habits from its training answers.
